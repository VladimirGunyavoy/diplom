## 1. Алгоритм спор по шагам

### 1.0 Задача
Система $\dot x = f(x,u)$, $x\in X\subset\mathbb R^n$, $u\in U$ (коробка или ромб). Цель $G$. Нужно найти управление $u(t)$, которое приводит
**любой** старт $x_0$ в $G$ за минимальное время:
$$V(x_0)=\min_{u(\cdot)} T\quad\text{при}\quad x(0)=x_0,\; x(T)\in G,\; x(t)\in X_{\text{free}} .$$
Идея: один раз покрыть фазовое пространство «спорами» (кусками точных траекторий при постоянном $u$), связать их в граф, посчитать на графе
цену до цели $V$. После этого запрос из нового старта — быстрый спуск по готовому $V$, без решения задачи оптимального управления заново.
Пространство покрывается один раз и обслуживает много стартов (а при retarget — и много целей). Это и есть ниша метода: «граф построен, гоняемся за целями» (`concepts.md`, слово пользователя 2026-10-12).

### 1.1 Слои по управлениям [А]
Оптимум быстродействия при линейном входе — bang-bang: $u$ лежит в вершинах $U$ (плюс дрейф $u=0$ — у финиша и на особых дугах).
Поэтому берётся конечный набор $u_1,\dots,u_L$: вершины $U$ ($\pm1$ по каждому каналу) и, где нужно, $0$. Каждому $u_\ell$ соответствует
**слой**: поле потока $f(\cdot,u_\ell)$ (`concepts.md` §Концепции клеток: «спектр управлений»).
Пример (ДИ 2D: $\dot p=v,\ \dot v=u,\ |u|\le1$): слои $u\in\{+1,-1,0\}$; клеток в слоях 1735 / 1880 / 1115 (`bench/table_di.md`).

### 1.2 Спора (клетка) — трубка траекторий одного слоя
В точке-затравке $p$ слоя $u_\ell$ берётся «заплатка» поперёк потока (сечение, ⟂ $f(p,u_\ell)$) и проносится потоком вперёд и назад
шагами $\Delta t$ — получается трубка траекторий с узлами-точками (строки вдоль потока × узлы поперёк).
Размер ограничен точностью локальной модели: вдоль потока $\tau\lesssim1$ с, поперёк полуширина $r\lesssim0.2$; клетка растёт, пока изгиб
сечения в метрике грамиана управляемости не превысит допуск ($\delta = 0.03$):
$$\delta x(t)\approx \Phi(t,t_0)\,\delta x(t_0),\qquad W=\int\Phi B B^\top\Phi^\top dt,\qquad \text{«цена» сдвига}\ \delta x^\top W^{-1}\delta x .$$
(`concepts.md`, `knowledge/research/cell_metric.md`, код `spores_2/v7/src/cells7/growN.py`.)
Посев — **повсеместный**, новая клетка — только в непокрытую точку; перекрытие соседей ≤ ~10–20% (`concepts.md`). Запрещённые
состояния (диски, стол, самостолкновение, стены лабиринта) — одна функция $g_{\text{free}}(x)\ge0$: клетка не растёт в запрещённое (FORB).

### 1.3 Граф и цена до цели (solve)
Узел графа — точка траектории своего слоя. Два вида рёбер (`concepts.md`, `solve_bucket.md` §РЕШЕНИЕ):
- **своё $u$:** точное ребро в следующий узел той же траектории, цена $= \Delta t$;
- **переключение $u_\ell\to u_m$:** в той же точке перейти в слой $u_m$; $V$ там берётся интерполяцией по вершинам ячейки слоя $u_m$ (стенсил,
  полилинейно по $2^n$ вершинам).

Цена до цели — уравнение Беллмана на графе:
$$V(i)=\min\Big(\Delta t + V(\text{next}_\ell(i)),\ \min_{m\ne\ell}\ \sum_j w_{ij}^{(m)}V(j)\Big),\qquad V|_G=0 .$$
Решается итерациями Якоби на GPU или «по вёдрам $V$» (обработка узлов в порядке роста $V$; та же неподвижная точка, работы ×200 меньше —
`solve_bucket.md`: маятник 15.9 → 2.2 с [Ч]).

### 1.4 Запрос
Из старта $x_0$: агент на каждом шаге выбирает слой с минимальной $\Delta t + V$ (видит переключения по пути, момент переключения — точный),
у цели — финиш стрельбой (`shoot_pol`, короткая доводка длительностей последних дуг). Выход — последовательность $(u_k, dt_k)$; её
**независимо** интегрирует единый проверяльщик бенча RK4 ($h=.01$) и считает $T$ и успех (`bench_protocol.md` §1).

### 1.5 Смена цели (retarget) и смена препятствий
- **Атлас клеток (v7/v8):** слои и рёбра от цели не зависят ⇒ на новую цель — только новый solve $V$ (рёбра из кэша). Манипулятор 4D:
  361 → 11–14.5 с на цель [Ч] (`PLAN.md` SPD1, `bench/table_mg.md`). Лабиринт дд: retarget = solve 91–180 с [Ч] (`PLAN.md` состояние линии C).
- **Смена препятствий:** $g_{\text{free}}$ входит в рост клеток ⇒ слои строить заново (полная заготовка) [П — не мерили отдельно].

### 1.6 Второй вариант той же идеи — «коридор v6» (системы 6D/8D и статик кар)
Для высоких размерностей полный атлас дорог, поэтому строится только то, что нужно (`knowledge/research/multiquery_corridor.md`, `tree_directed_6d.md`):
1. **Обратное дерево от цели** (NB спор, `build_back`) — строится **на каждую цель** (это и есть «переподготовка» коридора).
2. **Прямое дерево из старта** (NF спор) на запрос, раскрытие по A* с эвристикой из обратного дерева.
3. **Кандидаты стыковки:** прямая спора × ближайшие обратные ⇒ последовательность слоёв (топология). Промах не выбрасывается: score $= t + $ промах.
4. **Коридор:** K лучших топологий; для каждой — длительности дуг из задачи
$$\min_{dt_1..dt_m\ge0}\ \sum_k dt_k\quad\text{при}\quad x(\textstyle\sum dt)\in G,\ |\omega|\le3\ \text{на всём пути (wlim)},\ g_{\text{free}}\ge0,$$
   решается IPOPT (CasADi, точные производные; откат на SLSQP). Дерево даёт топологию, оптимизатор — точные длительности, поэтому $T$ ≈ эталону.

Результат сравнения ниже: споры держат $T/T_{\text{ref}}\approx1.00$–$1.05$ почти везде, где доходят; они проигрывают по весу (везде)
и по заготовке там, где у задачи есть аналитический локальный планировщик (ДИ, дифдрайв в свободном поле).

## 2. Как мерили (общее для всех таблиц) — `.llm/chain/knowledge/research/bench_protocol.md`
- **Заготовка:** споры — рост + solve; PPO — обучение; RRT/SST/kRRT\*/OCP — 0 (дерево/решение строится в запросе); PRM — карта.
- **Запрос:** стена, 1 CPU-процесс на запрос (если не указано иное). У RRT/SST/kRRT\* запрос = выделенный бюджет (anytime).
- **Вес:** споры — сумма `nbytes` массивов атласа/деревьев; PPO — `state_dict` + VecNormalize; RRT/SST — узлы дерева × байты на узел.
- **Успех:** попадание в $G$ при $T\le3T_{\text{ref}}$, без выхода из коробки/столкновения, по **единому проверяльщику** (RK4 $h=.01$).
- **$T_{\text{ref}}$:** ДИ — bang-bang; маятник — стрельба; дд — Balkcom–Mason min(TGT, TGTGT); манипуляторы — OCP CasADi/IPOPT мультистарт;
  8D, manipf, лабиринты — лучшее найденное среди методов (или нижняя граница — maze4).
- **Железо:** всё на aida — 32 ядра CPU (`table_m3d.md`: загрузка 20–25 из 32 при прогонах 6D/8D), GPU RTX 5070 Ti 16 ГБ (`concepts.md`).
  GPU — только у спор (solve, стенсилы) в ДИ 4D, манипуляторе 4D, dp1, лабиринтах; PPO учится на CPU (16 env).

## 6. Варианты подачи данных [П]
- **А. По системам (лестница сложности):** ДИ 2D → маятник → дд → дд+диски → кар → манип 4D (+запреты, +цели) → 6D → 6D+диски → 8D.
  Одна строка на систему: лучший соперник по каждому столбцу, споры подсвечены. Показывает, где метод выигрывает, а где нет. Плюс: честно и
  наглядно растёт размерность. Минус: много слайдов.
- **Б. По времени запроса (Парето «запрос × качество»):** точечный график, ось x — запрос (лог), ось y — $T/T_{\text{ref}}$, цвет — метод,
  размер — доходимость. Споры: мс–секунды при 1.00–1.05; PPO: мс при 1.1–4; SST: 60 с при 1.3–2; OCP: секунды–минуты при 1.00. Плюс: одна картинка
  на всё; минус: прячет заготовку и вес.
- **В. По полному времени total(K) и весу:** кривые total(N) (уже есть `total_*.png`) + столбик веса. Это формулировка пользователя
  («показать безубыточность; по весу проигрываем — так и планировалось»). Сильнее всего смотрится на CA4-A (K\*=31) и 6D (заготовка ~1 с).
Рекомендация: **Б** как обзорный слайд, затем **В** для 3–4 ключевых сред (manip 4D CA4, m3gd, m3gdg, dd+диски), таблица **А** — в приложение.
