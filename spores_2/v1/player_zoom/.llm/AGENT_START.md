## 🗣️ ОБЯЗАТЕЛЬНО: Задавай вопросы перед кодом

**Прежде чем что-то писать — спроси.** Пользователь ценит итеративный подход: сначала обсуждение, потом реализация.

### Какие вопросы задавать:

- **Цель:** «Что именно должна делать эта фича?»
- **Область:** «Только этот файл или затронет другие?»
- **Поведение:** «Как должно выглядеть для пользователя?»
- **Граничные случаи:** «Что если X — оставить старое поведение или изменить?»
- **Интерфейс:** «Нужен API вот такой или предпочесть другой?»

### Правило:

Если запрос **неоднозначный или затрагивает больше одного файла** — сначала опиши свой план и спроси подтверждение. Только получив «да» — пиши код.

**Лучше задать 2–3 лишних вопроса, чем переделывать готовое.**

## ⚠️ ВАЖНО: Что НЕ делать

### 🚫 Антипаттерны:

1. **НЕ делай массовых рефакторингов без запроса**
   - Пользователь попросил "исправить баг в ZoomManager" ≠ "переписать всю архитектуру"

2. **НЕ добавляй "улучшения" без обсуждения**
   - Не добавляй type hints везде, если только об этом не просят
   - Не рефактори код "по пути"

3. **НЕ удаляй print statements без запроса**
   - Они используются для дебага вместо логгера (осознанный выбор)

4. **НЕ меняй стиль кода без согласования**
   - Есть смесь русских и английских комментариев - это норма
   - Есть разные стили форматирования - это норма для песочницы

5. **НЕ предлагай "enterprise" решения**
   - Не нужен logging framework "для правильности"
   - Не нужны абстрактные фабрики и интерфейсы
   - KISS principle

6. **НЕ убирай существующий код без явного запроса**
   - Если что-то кажется лишним — спроси, не удаляй
   - Пример: авто-инжект ctx в ObjectManager — осознанный выбор, оставить

## 🔧 Технические особенности

### Dependency Injection:
```python
# Компоненты создаются сначала, потом регистрируются
manager = Manager()
component = Component()
manager.register_component(component)  # ← DI pattern
```

**Почему?** Избежание циркулярных импортов (см. `history/decisions.md`)

### TYPE_CHECKING:
```python
from typing import TYPE_CHECKING
if TYPE_CHECKING:
    from .other_module import OtherClass
```

Используется везде для избежания runtime циркулярных импортов.

## 🎨 Контекст из прошлых диалогов

### Математика зума:
Зум работает через **аффинное преобразование** с сохранением **инвариантной точки** (точка пересечения луча взгляда камеры с плоскостью y=0). Это ключевая фича проекта - не трогай без понимания математики.

### Watcher:
`run.py` + `src/watcher.py` - автоперезапуск при изменении файлов. Используется в разработке вместо ручного перезапуска.
