# Дрон R20 — лечение недошедших стартов (worker-37)
Код — копия b17 (`bench/w37_drone/`: spores_drone_e_w37.py, corridor_nd_w37.py с параметром vfy, dr.sh); запуск `dr.sh TAG "ENV…" сиды`; агрегат `agg_drone.py <папка>`. Данные: bench/data/drone_r20_fix{,v}/.
## Диагноз (по json R20 + DIAG на срезе подбора)
- no_path, тип A (90, 50): стыки есть (206–216 попаданий), но топ-5 топологий SLSQP отвергает → лечится K=20 (больше топологий).
- no_path, тип B (28, 3): стыка нет (nh=0) — прямое дерево NF1600 без направления не доходит на длинных маршрутах (T_OCP 6–7 с) → A*-эвристика прямого дерева HFW·(G_b ближайшего узла обратного дерева + расстояние); без OCP.
- touch (35 из 67; старты 79, 51, 58, 34): refine «ок», а проверка среды (Эйлер .02) даёт касание в узле шага (глубина до −3.6, т.е. план проходит сквозь препятствие) → отбрасывать кандидатов, не прошедших проверку среды, до выбора лучшего (VFY=1).

## Время запроса (worker-37, подбор STARTSEED 1, зёрна 20–29, 1000 запросов; PROCS 8, aida 1 под нагрузкой; t_query включает все проходы)
Профиль (`bench/w37_drone/prof37.py`, `phase37.py`): хвост > 5 с (19 из 1000, ≈10% суммарного времени) — только старты с повторами (RETRY 1–3: каждый повтор = полный проход ≈3 с). Типичный «3-секундный» старт (p90): проход NF1600 даёт кандидата, но проверка среды (VFY) его отбрасывает → запасной проход NF6400: кандидаты 1.26 с (43%) + ≈54 дожимов SLSQP 1.2 с (40%) + NF1600-проход .3 с. Внутри: деревья/кандидаты ≈60%, SLSQP ≈40%; из горячих мест flow/f6/clr/tree_query/HF — каждое 5–10%.

**Вывод:** цель p90 ≤ 2 с / max ≤ 5 с при 1000/1000 тем, что не меняет планы, НЕ достигается (кэш дерева — ≈0–10%). Любое ускорение запасного прохода (меньше NF/K) или отказ от повторов даёт p90 2.4–3.0 и max 3.9–8.8 ценой 13–32 недошедших на 1000. Время и доходимость здесь обратно связаны: ≈3 с на запасной проход — это 6400 узлов прямого дерева + десятки SLSQP. Реальное ускорение — структурное: (а) A*-дерево с жёсткой границей (HFW большей, но с проверкой доходимости) чтобы хватало NF1600; (б) переиспользование SLSQP-решений между топологиями (warm start); (в) распараллелить дожим топологий внутри запроса (ядра свободны, запрос ≈ один поток). Не сделано.

## Латентность: параллельный дожим топологий внутри запроса (PARQ=8; worker-37, aida 1, «один запрос за раз»: PROCS=1, 100 стартов STARTSEED 1, зёрна 20 и 23; данные `bench/data/drone_lat/`)

Ускорение ограничено долей последовательной части (деревья/кандидаты ≈60% прохода — Амдал). Следующий шаг без смены планов: запасной проход (кандидаты NF6400, 1.26 с) считать спекулятивно параллельно с первым проходом.
**Спекулятивный запасной проход (SPECFB=1: кандидаты NF6400 считаются в соседнем процессе параллельно первому проходу) — ОТРИЦАТЕЛЬНЫЙ результат.** Планы те же (100/100 на з.20 и 23), но латентность хуже: з.20 мед .58 / p90 3.00 / max 12.3 (было с PARQ .50 / 2.15 / 7.9), з.23 .82 / 4.05 / 15.9 (было .48 / 1.92 / 7.2); CPU Σ 221 и 333 с (было 151 и 156). Причина: большинство запросов доходит с первого прохода, спекуляция впустую занимает ядра пула и мешает дожиму. По умолчанию выкл., не используем; финальный вариант латентности — PARQ=8 без SPECFB.
