## Что у нас сейчас (HexIdx) и что делает ближайший готовый аналог
Равномерные бины QB^n → список гиперъячеек → bbox-отсев → аффинный предфильтр (J⁻¹ в центре, MG .4) → Ньютон n×n. **Это ровно конвейер findpts/Mittal 2025** (arXiv 2501.12349, LLNL/MFEM, GPU): равномерная «карта» → AABB элемента → **ориентированный OBB** (линейный образ по Якобиану в центре; у нас — `_prep`) → **Ньютон с доверительной областью, шаг ограничен r∈[−1,1]^D** (вне элемента сходится к ближайшей точке границы). 5 итераций хватает даже для высокого порядка. Т.е. структура у нас стандартная; вопрос только в размере бина и нескольких уровнях.

## (1) Walking от прошлой ячейки (запросы идут вдоль траектории)
Stencil walk / visibility walk: из ячейки прошлой точки шагать через грань, в сторону которой вышла точка (Sadarjoen 1998; Delft, снипп.). Запрос O(1) при малом шаге вместо O(бин+кандидаты). Риски (снипп.): на невыпуклых областях/дырах — зацикливание; сильно скошенные гекса-ячейки ломают разбиение на тетраэдры (5-тет. разбиение, предложено 6); PICLas признаёт «нет самопроверки» и ставит перелокализацию как страховку. Для нас: траектория в клетке идёт вдоль строк ⇒ walking внутри клетки хорош; при переходе в ЧУЖУЮ клетку (нет соседей по грани, клетки не стыкуются) walking не работает ⇒ нужен глобальный индекс. Моё: гибрид «сначала соседи прошлой ячейки, промах → индекс».
## (2) Пересечения клеток между собой (broad phase)
Sweep-and-prune (сорт. концов bbox по оси, пары, перекрытые по всем осям; insertion sort при малом сдвиге — Capannini–Larsson 2016, снипп.; Baraff-подход) — на 1–3 осях, в nD обычно сортируют по 1 оси с наибольшим разбросом ⇒ быстро для нашего случая (клетки растут, но не двигаются; пересортировка не нужна). Spatial join двух R-tree (Brinkhoff–Kriegel–Seeger 1993; BFRJ 1997, снипп.) = одновременный спуск, отсев пар неперекрытых узлов. Хэш-сетка: пары в одной бине. Моё: для «где клетки пересекаются» дёшево: BVH-самосвязь (спуск пар) либо sweep по самой «длинной» оси + проверка AABB по остальным; точное пересечение — Ньютон по вершинам одной клетки в карте другой (как наш `_test`).
## (3) Момент входа траектории в клетку
Стандарт ODE-солверов: смена знака события g(t,y) на шаге + корень на плотном выводе (scipy `solve_ivp events`, LSODAR/ODEPACK; снипп.). Известный провал: два пересечения внутри одного шага не видны. Для нас g = «координата в карте клетки пересекла 0/1» (sc из Ньютона `_test`) или «точка внутри» — булева функция, поэтому: бисекция по dt (у вас уже есть) ≈ log₂(dt/ε) обращений; быстрее — секущая/Brent по sc (гладкая функция, корень по координате клетки) — моё. Расстояние до границы в координатах клетки (sc) даёт оценку, сколько шагов до входа: шаг можно брать по max |ṡ|.
## (4) Что векторизуется, nD
numpy: уже так (HexIdx). Узкое место — Python-цикл по бинам в `query` (zip(uk,…)). GPU: Mittal 2025 — отдельные ядра для вычисления-доминирующих частей (Ньютон), индекс — по карте. Построение BVH на GPU — LBVH/Karras (сортировка Morton + один проход), в 4–6D Morton из 6 осей влезает в 63 бита (10 бит/ось) — совпадает с нашим `_key` (1024^n). Проклятие размерности: сетка/дерево с 2ⁿ ветвлением — плохо, хэш по занятым и BVH — терпимо; k-d — ok при n≤6.
## (5) Инверсия полилинейной карты
Условия обратимости гекса: Knabner–Korotov–Summ 2003 (знак детерминанта Якоби по вершинам; снипп.); точных необходимых и достаточных условий для 3D полилинейного элемента не известно (снипп. mesh-optimization). Надёжность: Ньютон из центра + проекция шага в [0,1]ⁿ + доверительная область (Mittal) вместо наших отбросов «вылетевших за −.2/1.2» (у нас точка вне ячейки отбрасывается — это норма для point-in-cell, не для «ближайшей»). Вырожденные ячейки (J≈0): у нас `+1e-12·I` — слабо; trust-region/LM (J+λI) надёжнее (моё). Альтернатива: разбиение на симплексы (n! тетра-подобных на гиперкуб) — линейно и надёжно, но разбиение не единственно и ломается на косых ячейках.
