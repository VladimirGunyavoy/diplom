# Прямое дерево с A*-эвристикой из обратного — бюджет NF в 6D (hub-research-4, 2026-10-01)
**Вопрос:** в 6D (3 звена+g=.3, цель вниз, DT=.02) worker-7 решал все 4 запроса только при NB12000 NF3000 (`knowledge/v6_findings.md`).
Нужен ли такой бюджет, или прямое дерево растёт не туда?
**Ответ:** растёт не туда. Если внутри уровня переключений раскрывать узлы по A* (g + 3·h, где h — время ближайшей обратной споры
+ расстояние до неё), то NF800 решает q1 (T 2.77, как база при NF3000), а NB6000 NF3000 — 4/4 валидно (база — только при NB12000).
T у q2 хуже (4.37 против 3.48 при NB12000).
## Почему (вывод по коду `adaptive_nd._tree`)
Приоритет sw_w·n + g, sw_w = 10 ⇒ дерево — перебор **по числу переключений**, внутри уровня — «шар» по времени. В 6D лучи без
переключения короткие (|ω| ≤ 3 за 2–3 шага τ): у прямого дерева 0 переключений ≈ 20 узлов, 1 переключение ≈ 300, всё остальное — уровень 2.
Гистограмма при NF3000: [18 288 2694]. Бюджет сверх ~300 тратится на 2-переключенные узлы **во все стороны** (L = 8 слоёв); на уровне k
растёт как ~(m·(L−1))^k, m ≈ 3–5 шагов на дугу. A* меняет только порядок внутри уровня: первыми идут узлы у обратного дерева.
Структура «сначала мало переключений» остаётся (в DI чистый A* без неё проваливался — `v6_findings.md`, строка про DI BFS/A*).
## Проверка
Прототип `reports/research/tree_directed6.py` (копия `_tree` + h из KD обратного дерева; подменяет `corridor_nd._tree`),
aida `~/spore_v5/r4/*.log`. Та же постановка, что `tests/check_corridor_manip6.py` G=.3 DOWN=1 DT=.02, NB6000, K5, tries 3, валидность —
мелкий rk4 dt .005 (конец в окне). Попадания candidates (без SLSQP) / T коридора:
| прямое дерево | q1 | q2 | q3 | q4 | валидно |
|---|---|---|---|---|---|
| база NF800 | 0 / — | 0 / — | 36 / 1.78 | 10 / 1.63 | 2/4 |
| A* wh3 NF800 | 30 / **2.77** | 0 / — | 52 / 1.78 | 56 / 1.61 | 3/4 |
| A* wh3 SW2 NF800 | 59 / **2.74** | 0 / — | 68 / 1.78 | 114 / 1.61 | 3/4 |
| база NF3000 (worker-7) | 31 / 2.77 | 0 / — | 74 / 1.78 | 117 / 1.61 | 3/4 |
| A* wh3 NF3000 | 47 / 2.77 | 7 / **4.37** | 74 / 1.78 | 137 / 1.61 | **4/4** |
| база NB12000 NF3000 (worker-7) | 2.77 | 3.48 | 1.78 | 1.61 | 4/4 |
Мин. расстояние прямое→обратное (метрика `diag_cover_6d.py`): q1 .131 → .073 (NF800), q2 .149 → .088 (NF800) / .072 → .054 (NF3000).
Варианты wh1/kap1, wh1/kap3, wh3/kap1 близки, лучше всего wh3 (сильнее тянет к обратному дереву). Время построения то же (3–11 с).
## Что нужно worker'у
1. В `adaptive_nd._tree` (только прямое, fwd=True) приоритет: `sw_w·n2 + g + wh·h(e)`, h(e) = Gb[b*] + kap·|e−b*|_scaled, b* — ближайшая
   обратная спора (KD `back[5]`, `% len(Pb)`), wh = 3, kap = 1; `candidates()` передаёт `back`. Тест: 6D+g NB6000 NF800 → ≥ 3/4 валидно.
2. Перемерить таблицы 6D/4D с меньшими NF (ожидание — NF ×3–4 меньше при том же результате). q2 при NB6000 даёт T 4.37 против 3.48 при
   NB12000 — для качества NB по-прежнему нужен; A* лечит покрытие, а не оптимальность.
3. Гипотеза (не проверена): SW = 2 вместо 10 вместе с A* ещё лучше (q1 2.74, больше попаданий); и A* для обратного дерева к «облаку»
   стартов (многозапросность) — отдельный эксперимент.
