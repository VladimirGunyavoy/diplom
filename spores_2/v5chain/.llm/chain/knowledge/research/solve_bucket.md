# solve по вёдрам V (упорядоченная коррекция меток) вместо Якоби/ГЗ — research-21, 2026-10-07 04:30
**Вопрос:** почему solve дорог (маятник 441–1372 итерации, di4 175 × 3 с, manip c9000 60 с/итерацию) и почему ГЗ/рабочий список не помогли (b4: GS 241 против 268; w23: solve_wl 66% рёбер за итерацию)?
**Ответ одной фразой:** Якоби/ГЗ двигают фронт V на один шаг DTN за проход ⇒ ≈ Vmax/DTN проходов по ВСЕМ рёбрам; если обрабатывать узлы
в порядке V (ведро ширины D = DTN), каждое ребро считается 2–3 раза — **V та же до бита, работа ×200 меньше**.

## Алгоритм (прототип `reports/research/r18/solve_bucket.py`, функции `edges` + `solve_bucket`)
1. Рёбра те же, что в `Atlas.solve` (стенсилы I/IDX/W, стоимость DTN; NFEDGE/MROW-связки как рёбра с 1–2 вершинами).
2. Обратный индекс CSR: вершина → рёбра, где у неё вес > 1e-6 (argsort по вершине + searchsorted).
3. `pend` = узлы с изменившейся, но не разосланной V (вначале — цель и узлы с конечной tgoal). Порог θ = min V[pend]; thr = θ + D.
4. Пока есть pend с V < thr: взять их (снять с pend), рёбра всех узлов-зависимых (обратный индекс) пересчитать (`interp`, BIG-правило то же),
   min по узлу (`reduceat`); улучшилось > tol (1e-9) — записать V, узел в pend; если новая V < thr — он в этот же внутренний цикл.
5. θ = thr, следующее ведро; конец — pend пуст.
Точность: это коррекция меток (label-correcting) — узел, улучшенный позже, снова рассылается ⇒ та же неподвижная точка монотонного оператора, что у Якоби
(не Дейкстра с окончательными метками: интерполяция не строго причинна, поэтому без «финализации»). Порядок по V — только для скорости.
Отличие от `solve_wl` w23: рабочий список без порядка рассылает каждое мелкое улучшение сразу ⇒ узел улучшается ~Vmax/DTN раз; с порядком — 2–3 раза.
