# bench_protocol — честное сравнение спор с RRT / SST(RRT*) / PPO / OCP (research-25, 2026-10-12; линия C, worker-c1)
**Вопрос:** как поставить сравнение, чтобы вывод «споры быстрее» (слово пользователя) был проверяем, а не следствием слабых конкурентов?
**Ответ:** один класс задач (фиксированная цель, любой старт из поля, минимум времени), одна проверка траекторий, конкуренты из библиотек
с параметрами по литературе + малый свип, время раздельно (построение / запрос) и кривая «качество от времени»; выигрыш формулируем через
точку окупаемости N* (число запросов), а не одним числом.

## 1. Постановка (одинаково для всех методов)
- Задача: цель G (шар/ящик среды), старт из S, min T, |u| ∈ U среды. Это ровно класс спор и PPO (одна цель, любой старт); RRT/SST — одиночный запрос.
- Старты: 20 на среду, `Env.X0` (seed 1); манипулятор 4D — 20 стартов эталона OCP `r23/manip_ref_ocp_20.npy`. Старт, у которого эталонная
  траектория выходит из поля, исключается **для всех методов** (решение пользователя по v8: «вне метрик»), число исключённых — в отчёт.
- Успех: попадание в G при T ≤ 3·T_ref, без выхода из коробки (и без столкновений, где есть препятствия).
- **Единый проверяльщик:** каждый метод отдаёт последовательность (u_k, dt_k); `bench` сам интегрирует её RK4 (h .01, точный шаг у ДИ) из
  старта и считает T и успех. Внутренней модели метода не верим (ни своей, ни чужой).
- Эталон T_ref: ДИ `ref_di_disk`, маятник `pend_ref_T` (стрельба), дд Balkcom–Mason min(TGT, TGTGT), манипулятор OCP r23.

## 2. Что мерить (столбцы таблицы)
среда | метод | параметры | t_build (споры: рост+solve; PPO: обучение) | t_query мед/p90 | t_total(N=20) | на запрос при N = 20 / 1000 |
дошли % | T/T_ref мед/mean/p90/max | вызовов f (RK4-шагов) | железо.
- **Слово пользователя 2026-10-12 21:12 (через research-5) — обязательные столбцы и график:** (1) время заготовки везде: споры — рост+solve, RRT/SST/kRRT* —
  построение дерева (одиночный запрос: дерево строится в запросе ⇒ заготовка 0, запрос включает дерево; вариант «обратное дерево от цели, раз на все
  запросы» — заготовка = дерево), PPO — обучение; (2) **вес данных**: споры — узлы/рёбра графа + V + геометрия клеток (шт. и байты: сумма `nbytes` массивов
  и размер файла атласа), PPO — параметры сети (шт.) и байты `state_dict` + VecNormalize, RRT — узлы дерева × байты на узел (на конец запроса);
  «наш алгоритм будет проигрывать по весу, но таков в целом план был»; (3) итог — **кривая полного времени total(N) = заготовка + N·запрос** по каждому методу
  (лог-лог, N 1…1e5) и точки безубыточности «с какого N споры выгоднее» (и наоборот) — график на каждую среду.
- Амортизация: total(N) = t_build + N·t_query. Для каждого конкурента — **N\*** (окупаемость) при сопоставимом качестве (T/T_ref мед не хуже).
- **Кривая anytime** для SST (и RRT*-ДИ): T/T_ref мед и доля дошедших при бюджетах 0.3 / 1 / 3 / 10 / 60 с на запрос; споры — точка + горизонталь.
- **Счёт вызовов f** (обёртка-счётчик на `Env.f`/`step`) — мера, не зависящая от языка: у OMPL ядро на C++, но динамика — колбэк на Python;
  у спор numpy/GPU. Оба времени (стена и вызовы f) — в таблицу.
- Железо: всё на aida. Основная таблица — CPU, 1 процесс на запрос (`OMP_NUM_THREADS=1` и т.п.). GPU (solve спор, обучение PPO) — отдельный
  столбец/пометка; если solve спор на GPU, а PPO учится на CPU (или наоборот) — пометка в строке.

## 3. Конкуренты по литературе (не чучела)
- **RRT кинодинамический** (LaValle–Kuffner 2001): OMPL `control::RRT` (pip `ompl` 2.0.1 есть под cp312 — ставить в отдельный venv на aida),
  goal bias .05 (дефолт OMPL), управление — равномерно в U (непрерывно, не только наши слои ±1/0: это даёт ему больше, не меньше),
  длительность [1, 20] шагов propagation h .05 (порядок τ системы), метрика — `Env.embed` (углы через sin/cos).
- **«RRT\*» для систем с динамикой = SST** (Li–Littlefield–Bekris 2016, IJRR; асимптотически почти-оптимален без решателя краевой задачи —
  стандартная замена RRT* в кинодинамике), OMPL `control::SST`: selection .2 / pruning .1 (дефолт) + свип {.05, .1, .2, .4} на 5 стартах,
  берём лучший, свип — в отчёт. Для ДИ (линейная система) дополнительно настоящий **kinodynamic RRT\*** с точным управлением между
  состояниями (Webb–van den Berg 2013; у ДИ мин.-временная краевая задача аналитическая, bang-bang) — сильнейший честный конкурент на ДИ.
- **PPO** (Schulman 2017), SB3 2.9 + torch (aida, `~/Calf_Barrier_Safe_MHLB_Code/.venv-sb3`): гиперпараметры rl-zoo для Pendulum-v1 как
  старт; награда −dt за шаг, +бонус в цели, конец эпизода — цель/выход/3·T_max; формирование потенциалом (Ng–Harada–Russell 1999,
  оптимум не меняет) — можно; VecNormalize; непрерывное действие в U (дд — проекция на ромб); бюджеты 1M и 5M шагов, 3 сида — лучший и среднее;
  оценка deterministic на тех же стартах тем же проверяльщиком. t_train до 95% успеха — отдельной цифрой.
- **OCP на запрос** (SLSQP/прямая стрельба, как эталон): время на запрос; инициализация — без знания числа переключений (иначе пометка).

## 5. Гипотезы (проверить, не утверждать)
- Запрос: споры мс–сотни мс против секунд у SST при T/T_ref ≤ 1.1 ⇒ N\* мал (единицы–десятки). На ДИ kRRT* с точным краевым может быть
  быстрее спор даже на запрос — тогда так и пишем.
- PPO: инференс быстрее спор (< 1 мс); обучение (десятки минут–часы) против построения спор (секунды–минуты) ⇒ выигрыш — в t_build и T/T_ref.
- 4D: build спор ~10 мин — это наш слабый режим против одиночного запроса; честно показать N\*.
