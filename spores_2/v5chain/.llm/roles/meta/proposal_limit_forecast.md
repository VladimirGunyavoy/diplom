## Правила
Обозначения: p5, p7 — текущие %; h5, h7 — часы до сброса 5ч/7д; r — темп аккаунта, %5ч/ч; q — темп нового агента по роли; H — длина смены; k = 0.13.

- **A. Возраст данных** = время с последней записи аккаунта с выросшим `cost_usd` (был API-ответ), по логам всех машин; mtime не использовать.
  `hub_usage_sync.py` — в cron ноута. Лог — один на машину (или pick_account читает все логи проекта, не только cwd).
- **B. Темп r** = прирост p5 за последние 30 мин, правый край — «сейчас» (простой > idle_minutes → 0, как в 8f1820b).
- **C. Темп нового агента q** — по роли (`--role`): таблица %/ч в `accounts.json` (старт: research 10, worker 8, searcher 4, fixer 3, meta 3,
  без роли — 10), пересчитываемая из лога (медиана $/ч роли × %/$ аккаунта). Резерв недавних спавнов: +q·время, пока у новой сессии нет
  первых записей с расходом (вместо «+35% на 10 мин»).
- **D. 5ч — по простою.** t_ст = (100 − p5)/(r + q). t_ст ≥ min(h5, H) → годен, простой 0. Иначе простой = h5 − t_ст; годен при простое ≤ 20 мин
  (`max_stall_min`). У всех больше → пусто и «ждать до T» (ближайший момент, когда условие выполнится).
- **E. 7д — по запасу в час.** g = (100 − p7)/h7 (% недели в час); среди годных по D побеждает больший g (тай-брейк — меньший простой).
  Стена: p7 + k·(r + q)·min(H, h7) < 98 (`seven_day_wall`), иначе аккаунт исключён. Жёсткий отсев «7д ≥ 90» и ранжирование «минимум 7д» убрать.
- **F. Предупреждение** в `--why`: k·r > g → «этим темпом неделя кончится через (100−p7)/(k·r) ч, раньше сброса».
- **G. Устаревшие данные** (возраст по A > idle_minutes) у аккаунта с p7 ≥ 80: сначала проверить, даёт ли дешёвый пробный запрос на аккаунт
  свежие rate_limits (не проверено — выяснить); работает — пробовать перед решением; нет — считать p5/p7 нижней границей и аккаунт не выдавать,
  пока не появятся свежие данные (лог другой машины или сброс окна по resets_at).
