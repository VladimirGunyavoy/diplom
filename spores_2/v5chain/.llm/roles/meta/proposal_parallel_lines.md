# Предложение: параллельные линии для любой роли (hub-v5chain-meta-2, 2026-10-06)
Задача пользователя (15:35/15:42): «структурируй историю, чтобы ресерчер мог запускать параллельно много воркеров, вряд ли больше трёх;
протокол для любых ролей»; «в целом должна быть опция запускать параллельные роли». Сейчас есть частный случай — две линии worker'ов
(`WORKER_ROUTINE.md` §Две линии, схема research-15, не утверждена).

## 1. Линия — параллельная эстафета одной роли
- **Имя:** `<маш>-<проект>-<роль>-[<буква>]N`. Линия A — без буквы (все текущие имена не меняются), B — `…-b1`, C — `…-c1`.
  **Не больше трёх линий на роль.** Номер внутри линии свой, сквозной: преемник `…-b3` — `…-b4`. Скрипты это уже понимают (`NAME_RE`).
- **Кто открывает:** тот, кто ставит роли задачи. worker — research (или пользователь); research, searcher, explainer — пользователь
  (или research с его слова); dispatcher — одна на все линии, линий не бывает; fixer — пул без линий, как сейчас (`call_fixer.py`).
- **Открыть** = строка в `JOURNAL.md` `<кто> | line-open | <роль> <буква> | <зачем, какие задачи PLAN>` + спавн `…-<буква>1`.
- **Закрыть:** очередь линии в `PLAN.md` пуста и новых задач ей не дают → последний агент линии пишет `done | … | next=— (линия B закрыта)`,
  преемника не поднимает; хендофф линии остаётся как история. Решает тот же, кто открыл (или агент сам, если очередь пуста и open-автор молчит 15 мин).
- Смена внутри линии — как обычно по рутине роли, с той же буквой.

## 2. История (память) линии
- **Линия A** — `.llm/roles/<роль>/` как сейчас (переезда нет).
- **Линии B, C** — подпапка `.llm/roles/<роль>/b/` с `HANDOFF.md` и `recent.md` (своя эстафета, ротация та же).
  `archive.md` — один на роль, записи линии с пометкой `[b]` (читают редко). `HANDOFF_b.md` → переносится в `worker/b/HANDOFF.md`.
- **Номера экспериментов** — буква линии перед номером: `b17` (как в имени); у A — без буквы. Уже выданные 300+ линии B не переименовывать.
- **Задачи** в `PLAN.md` — тег линии в заголовке задачи `[B]`; без тега — линия A. Раздаёт тот, кто открыл линию.

## 3. Общие файлы — кто пишет
Все линии работают в одном дереве на хабе (не клоны) — конфликт не на `git pull`, а на одновременной правке одного файла.
- `JOURNAL.md` — только дописывание `>>` одной строкой (атомарно), как сейчас.
- `STATUS.md` — у каждой открытой линии свой подраздел `### Линия B`; правишь только свой; общий раздел — research/dispatcher.
- `PLAN.md` — пишет владелец (research); исполнитель только отмечает статус своих задач (правка одной строки через `Edit`, не перезапись файла).
- `knowledge/`, код — **у файла один владелец-линия**: указывается в задаче PLAN («growN.py — линия B; A добавляет только блок своей
  системы»). Чужой файл — просьба владельцу или research'у, а не правка.
- Коммит — только своих путей (`git commit -- <пути>`), никогда `git add -A`/`commit -a`; `index.lock` занят — подождать и повторить.

## 4. Скрипты (задача fixer'у)
- `machine.current_workers` → `current_agents(journal, role)` (по одному на линию); `current_workers` оставить обёрткой.
- `sentinel.py … <роль> auto auto` и `pulse.py <роль> … auto` — для любой роли, не только worker (dispatcher сторожит все линии worker и research).
- `pick_account.py`: при 2–3 спавнах подряд учитывать уже поднятые за последние ~10 мин (резерв `shift_5h_pct` на каждый), иначе все
  три сядут на один аккаунт и вместе пробьют 5ч.
- `reap_idle.py` лимит 20 — хватает (3 линии × 2 роли + служебные), не трогать.
- `cron_guard`/`ПАДАЕТ` — проверить, что считает пульсы по полному имени с буквой.
