## Decision #1: Dependency Injection вместо прямых импортов

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
Циркулярные импорты при сложных зависимостях между менеджерами и компонентами.

```python
# ❌ Проблема:
# input_manager.py
from .zoom_manager import ZoomManager

# zoom_manager.py
from .scene_setup import SceneSetup

# scene_setup.py
from .input_manager import InputManager

# → Циркулярная зависимость!
```

**Рассмотренные варианты:**

1. **Прямые импорты** - не работает из-за циклов
2. **Отложенные импорты** (import внутри функций) - плохо для type hints
3. **Dependency Injection** - компоненты регистрируются после создания
4. **Event Bus** (pub/sub) - слишком сложно для песочницы

**Решение:** Dependency Injection (вариант 3)

**Реализация:**
```python
# Создаем менеджеры независимо
input_manager = InputManager()
zoom_manager = ZoomManager(...)

# Регистрируем зависимости после создания
input_manager.register_zoom_manager(zoom_manager)
```

**Type hints** через TYPE_CHECKING:
```python
from typing import TYPE_CHECKING
if TYPE_CHECKING:
    from .zoom_manager import ZoomManager  # только для IDE/mypy

class InputManager:
    def __init__(self):
        self.zoom_manager: Optional["ZoomManager"] = None
```

**Почему именно так:**
- ✅ Разрывает циркулярные зависимости
- ✅ Сохраняет type hints для IDE
- ✅ Явное управление зависимостями в main.py
- ✅ Гибкость - легко добавить новые зависимости
- ❌ Чуть больше boilerplate кода

**Альтернативы не выбраны:**
- Event Bus - overkill для небольшого проекта
- Отложенные импорты - теряем type hints

**Статус:** ✅ Активно используется

## Decision #2: Аффинное преобразование для зума

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
Как реализовать зум с сохранением точки взгляда (invariant point)?

**Требования:**
- При зуме точка, на которую смотрит камера, должна оставаться на месте
- Все объекты сцены должны масштабироваться
- Математически корректно (без накопления ошибок)

**Рассмотренные варианты:**

1. **Простой зум** - масштабировать все объекты вокруг (0,0,0)
   - ❌ Точка взгляда сдвигается

2. **Перемещение камеры** - двигать камеру ближе/дальше
   - ❌ Меняется перспектива, не совсем "зум"

3. **Аффинное преобразование** - `x' = a*x + b` с вычислением b для сохранения точки
   - ✅ Математически корректно
   - ✅ Точка взгляда остается на месте

**Решение:** Аффинное преобразование (вариант 3)

**Математика:**

Условие сохранения точки `p`: `p' = p`

```
a*p + b = p
b = p - a*p = (1 - a)*p
```

При изменении зума на коэффициент `k`:
```
a_new = k * a_old
b_new = k * b_old + (1 - k) * p
```

где `p` - инвариантная точка (look point).

**Реализация:**
```python
def change_zoom(self, sign: int):
    inv_point = self.identify_invariant_point()  # вычислить p
    zoom_multiplier = self.zoom_fact ** sign     # k

    self.a_transformation *= zoom_multiplier
    self.b_translation = zoom_multiplier * self.b_translation + \
                         (1 - zoom_multiplier) * inv_point
```

**Почему именно так:**
- ✅ Математически строго корректно
- ✅ Нет накопления ошибок (трансформация к real_position)
- ✅ Работает для любой точки
- ✅ Обобщается на 3D (пока используется 2D на плоскости y=0)

**Альтернативы не выбраны:**
- Перемещение камеры - не дает эффект зума
- Простой зум - точка сдвигается

**Источник:** Курс линейной алгебры / компьютерной графики

**Статус:** ✅ Активно используется

## Decision #3: NumPy для математики

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
Какую библиотеку использовать для векторных операций?

**Рассмотренные варианты:**

1. **Ursina Vec3** - встроенный в движок
2. **NumPy** - стандартная библиотека для научных вычислений
3. **Чистый Python** (списки/кортежи)

**Решение:** NumPy (вариант 2)

**Почему:**
- ✅ Привычный инструмент для математики
- ✅ Хорошая документация и community
- ✅ Богатый API (sin, cos, tan, radians, etc.)
- ✅ Эффективно для массовых операций

**Альтернативы не выбраны:**
- Vec3 - менее удобен для тригонометрии
- Чистый Python - слишком verbose

**Пример использования:**
```python
import numpy as np

psi = np.radians(player.rotation_y)
phi = np.radians(camera.rotation_x)

d = h / np.tan(phi)
dx = d * np.sin(psi)
```

## Decision #4: Scalable pattern

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
Как обеспечить что все объекты корректно масштабируются при зуме?

**Требования:**
- Трансформация должна применяться к **оригинальным** значениям
- Простота добавления новых объектов

**Рассмотренные варианты:**

1. **Вручную** - вызывать трансформацию для каждого объекта
   - ❌ Легко забыть
   - ❌ Дублирование кода

2. **Базовый класс Scalable** - наследование от Entity + apply_transform()
   - ✅ Автоматическая поддержка
   - ✅ Единое место для логики

3. **Component pattern** - добавлять ScalableComponent к Entity
   - ✅ Гибко
   - ❌ Сложнее для простого случая

**Решение:** Базовый класс Scalable (вариант 2)

**Реализация:**
```python
class Scalable(Entity):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.real_position = np.array(self.position)
        self.real_scale = np.array(self.scale)

    def apply_transform(self, a, b):
        self.position = self.real_position * a + b
        self.scale = self.real_scale * a
```

**Использование:**
```python
class MyFloor(Scalable):
    pass  # автоматически поддерживает зум

floor = MyFloor(...)
zoom_manager.register_object(floor)  # готово!
```

**Почему именно так:**
- ✅ Простота использования
- ✅ Невозможно забыть реализовать apply_transform
- ✅ Единое место для логики трансформации
- ❌ Наследование вместо композиции (но для простого случая ОК)

**Ключевая идея:**
Сохранять `real_position` и `real_scale` - **оригинальные** значения. Трансформация всегда применяется к ним, а не к текущим значениям. Это предотвращает накопление ошибок.

**Статус:** ✅ Активно используется

## Decision #6: Watcher для auto-reload

**Дата:** 2026-03-16 (начало проекта)

**Проблема:**
При каждом изменении кода нужно вручную перезапускать программу.

**Рассмотренные варианты:**

1. **Ручной перезапуск** - Ctrl+C → python main.py
2. **Watchdog** - библиотека для отслеживания изменений файлов
3. **Встроенный механизм Ursina** - ?

**Решение:** Watchdog (вариант 2)

**Реализация:**
```
run.py → watcher.py → запускает main.py → при изменении .py → перезапуск
```

**Логика:**
- Exit code 0 (нормальный выход) → автоматически перезапустить
- Exit code != 0 (ошибка) → остановиться (дать исправить)
- Ctrl+C → остановить watcher

**Почему именно так:**
- ✅ Ускоряет итерации разработки
- ✅ Не перезапускает при ошибках (чтобы прочитать traceback)
- ✅ Watchdog - надежная библиотека
- ❌ Дополнительная зависимость

**Альтернатива:** nodemon для Python - но watchdog достаточно.

**Статус:** ✅ Активно используется в разработке

## Decision #7: Структура llm/ для контекста

**Дата:** 2026-03-19

**Проблема:**
При работе через несколько диалогов с AI агентами:
- Теряется контекст проекта
- Приходится заново объяснять архитектуру
- Большое потребление токенов на передачу контекста

**Требования:**
- Минимизировать токены
- Сохранить адекватность контекста
- Структурированность и навигация

**Рассмотренные варианты:**

1. **Плоская структура** (все файлы в llm/)
   - Простота
   - ❌ Сложно навигировать при росте

2. **Вложенная структура** (context/, state/, history/)
   - ✅ Четкое разделение ответственности
   - ✅ Масштабируемость
   - Чуть сложнее

3. **Git-подобная** (.llm/refs/, .llm/objects/)
   - ❌ Overkill

**Решение:** Вложенная структура (вариант 2)

```
llm/
├── context/      # Редко меняется, базовые знания
├── state/        # Часто меняется, текущее состояние
└── history/      # Append-only, история
```

**Ключевые файлы:**
- `AGENT_START.md` - напутствие (читать первым!)
- `AGENT_END_ROUTINE.md` - чеклист завершения работы
- `context/start_prompt.md` - TL;DR + ключевые концепции
- `state/current.md` - что работает/не работает сейчас

**Принципы:**
- **Краткость** - TL;DR сначала, детали потом
- **Актуальность** - state/ обновляется каждую сессию
- **История** - history/ append-only
- **Навигация** - четкие ссылки между файлами

**Почему именно так:**
- ✅ Минимизирует токены (агент читает только нужное)
- ✅ Структурировано (легко найти информацию)
- ✅ Масштабируемо (легко добавлять новые файлы)
- ✅ Разделение по частоте изменений

**Inspiration:**
- Git (.git/ структура)
- Conventional Commits
- Project documentation best practices

**Статус:** ✅ Создано 2026-03-19

## Decision #8: Key binding через trigger-лямбды вместо on_input в объектах

**Дата:** 2026-03-19 (сессия 4)

**Проблема:**
При добавлении `on_input(key)` в каждый GameObject клавиши рассыпаются по объектам. Чтобы понять какие клавиши заняты — нужно смотреть в каждый класс.

**Решение:** Binding system с trigger-лямбдами в ObjectManager

```python
# Объект знает только о своих действиях:
class MyObject(GameObject):
    def increase_speed(self): ...

# Клавиши — только в main.py:
object_manager.bind(
    my_object.increase_speed,
    trigger=lambda key: key == '2' and not scene_setup.input_frozen
)
```

**Почему именно так:**
- ✅ Все клавиши видны в одном месте (main.py)
- ✅ Объект — чистая логика, без знания об input
- ✅ Trigger-лямбда = любые условия (frozen, key combos, held_keys)
- ✅ Легко перебиндить без трогания класса
- ❌ Немного verbose для простых случаев

**Статус:** ✅ Активно используется

## Decision #9: tick(dt) вместо update(dt) в GameObject

**Дата:** 2026-03-19 (сессия 4)

**Проблема:**
Ursina автоматически вызывает `Entity.update()` на всех Entity без аргументов каждый кадр. Если GameObject определяет `update(self, dt)` — Ursina падает с `TypeError: update() missing 1 required positional argument: 'dt'`.

**Решение:** Использовать имя `tick(dt)` вместо `update(dt)` в GameObject/ObjectManager.

**Почему именно так:**
- ✅ Нет конфликта с Ursina Entity lifecycle
- ✅ Явное отличие от ursina-update
- ✅ `tick` — устоявшийся термин для game loop step

**Статус:** ✅ Активно используется

## Decision #10: DoubleIntegrator вместо DiffDrive

**Дата:** 2026-04-19 (сессия 6)

**Проблема:**
DiffDrive (unicycle model, state=[x,y,theta], control=[v,omega]) слишком сложная модель для текущих задач. Нужна более простая система.

**Решение:** 1D Double Integrator — `x_ddot = u`

```
state   = [x, x_dot]
control = u  (скаляр)
```

**Реализация:** `src/math/double_integrator.py`
- Точное аналитическое интегрирование (нет накопления ошибок)
- Нет тригонометрии → нет особых случаев
- JIT-готов: `_step()` вынесена как отдельная функция
- Паттерны управления: bang-bang, `u ∈ {+1, -1}`

**Маппинг state → Ursina:** `pos=(x, 0, x_dot)` — phase portrait в плоскости xOz (позиция × скорость).

**Почему именно так:**
- ✅ Максимально простая система
- ✅ Аналитически точное интегрирование
- ✅ Классический phase portrait легко читается
- ✅ Хорошо для теоретических экспериментов

**Статус:** ✅ Активно используется

## Decision #20: Разделение рутины на стартовую и финишную (v2)

**Дата:** 2026-06-12 (сессия 17 / v3 сессия 3)

**Проблема:**
Финишная рутина (v1) выполняется когда контекст сессии максимально заполнен — дорого. Например, в сессии 16: Работа=8%, Рутина=5% — рутина стоила больше половины самой работы, потому что выполнялась поверх уже накопленного диалога.

**Рассмотренные варианты:**

1. **Всё в конце сессии (v1)** — просто, но рутина (changelog, decisions, обновление state/, git commit) каждый раз конкурирует с заполненным контекстом
2. **Handoff в конце, остальное в начале следующей сессии (v2)** — финишная рутина = только `session_handoff.md` (10 строк); стартовая рутина новой сессии (контекст почти пустой) обрабатывает handoff: changelog, decisions, state/, git commit

**Решение:** Вариант 2

**Реализация:**
- `AGENT_END_ROUTINE.md` — облегчён до: спросить токены → записать `session_handoff.md` с пометкой `[РУТИНА НЕ ВЫПОЛНЕНА]` → закоммитить только этот файл → спросить токены
- `AGENT_START_ROUTINE.md` — новый файл: спросить токены → прочитать handoff → обновить `state/*` → дописать `changelog_recent.md`/`decisions.md` → git commit рабочих файлов → спросить токены → записать `token_stats.md`
- `state/token_stats.md` — схема расширена до 4 точек: T_START, T_AFTER, T_BEFORE_END, T_END

**Почему именно так:**
- ✅ Тяжёлая часть рутины выполняется когда контекст пустой — не конкурирует с накопленным диалогом
- ✅ Финишная рутина становится дешёвой и предсказуемой (один файл, один коммит)
- ✅ 4 точки замера показывают стоимость каждой половины рутины отдельно

**Статус:** ✅ Активно

`BoundaryRayFamily` зависела от `GhostSporeFamily` как источника граничных узлов. Семья создавала визуальный шум, а концепция ветки (bang-bang с одним переключением) оказалась самостоятельной и не требует сетки семьи.

**Решение:** Удалить `GhostSporeFamily`, переписать `BoundaryRayFamily` как независимый `BranchFamily`.

**BranchFamily** вычисляет граничные узлы сама:
- Шаблон `((u1_sign, t1_sign), (u2_sign, t2_sign))`
- k=0..n_tau лучей: k шагов фазы-1, (n_tau-k) шагов фазы-2
- k=0 = чистая фаза-2, k=n_tau = чистая фаза-1
- Numpy-векторизация: один цикл по шагам, не по лучам

**Почему именно так:**
- ✅ Концептуально чище: ветка = самостоятельная сущность
- ✅ Устранена "каша" от двух семей + лучей одновременно
- ✅ n_u убран из параметров — не нужен
- ✅ Векторизация даёт запас по производительности при больших n_tau
- ❌ GhostSporeFamily потеряна (но это копия, не production)

**Статус:** ✅ Активно используется

## Decision #15: Grid-триангуляция вместо fan по boundary

**Дата:** 2026-05-26 (сессия 14)

**Проблема:**
`ScalableFanSurface` использовала triangle fan от рута через упорядоченную boundary-кривую. Часть треугольников давала двойное перекрытие → пятно на поверхности.

**Корень:** Boundary (k=0 луч вперёд → фронтир → k=n_tau луч назад) не является star-shaped многоугольником относительно рута. k=0 луч уходит по часовой стрелке (угол –49°→–63°), затем фронтир прыгает обратно до –28°. Переходный треугольник `(root, B[3], B[4])` накрывал сектор –63°…–28°, перекрывая треугольники k=0 луча.

**Решение:** Прямая grid-триангуляция по `positions[k, step]`:
- fan: `(root, positions[k,0], positions[k+1,0])` — n_tau треугольников
- grid: квады `positions[k,j]..positions[k+1,j+1]` — 2*n_tau*(n_tau-1) треугольников

**Почему именно так:**
- ✅ Топология точно соответствует математической структуре данных
- ✅ Нет перекрытий по построению (соседние лучи не пересекаются)
- ✅ Проще API: передаём `positions` напрямую, не строим boundary
- ❌ Больше треугольников при больших n_tau (n_tau*(2n_tau-1) vs 3n_tau-2)

**Статус:** ✅ Активно используется

## Decision #19: Pluggable dynamics model через shared_context.model

**Дата:** 2026-06-12 (сессия 16)

**Проблема:**
`BranchFamily._recompute()` использовал инлайн-формулу double integrator (`x + v*dt + 0.5*u*dt²`). Чтобы экспериментировать с нелинейной динамикой (маятник), формулу пришлось бы дублировать или писать if/else по типу модели.

**Решение:** Любая модель динамики реализует общий интерфейс `step(x0, v0, u, dt) -> (x, v)` и кладётся в `shared_context.model`. `BranchFamily` зовёт `self._ctx.model.step(...)`, не зная какая это модель.

```python
# main.py
model = Pendulum(shared_context)   # <- меняй класс, чтобы сменить динамику
shared_context.bind('model', lambda: model, default=model)
```

`DoubleIntegrator.step()` приведён к тому же интерфейсу (возвращает `(x, v)` вместо `np.array`).

**Конвенция для `Pendulum`:** `θ=0` — нижнее устойчивое положение, `θ̈ = -sin(θ) + u` (g/l=1, m·l²=1). Изначально был `InvertedPendulum` с `θ=0`=верх (`θ̈ = sin(θ)+u`), но решили, что нижнее положение интуитивнее для экспериментов — переименовали и сменили знак.

**Почему именно так:**
- ✅ Переключение динамики — одна строка в main.py
- ✅ `BranchFamily` не знает о конкретных моделях (DI-стиль, как остальной проект)
- ✅ Векторизация сохраняется — `step()` принимает numpy-массивы для обеих моделей

**Статус:** ✅ Активно используется

## Decision #21: OrthoGrid заменяет BranchFamily

**Дата:** 2026-06-20 (сессия 20 / v4_ort сессия 1)

**Проблема:**
BranchFamily показывала ветви bang-bang управления (u₁→u₂), но не давала интуитивной картины потока: как деформируется окрестность точки в фазовом пространстве при фиксированном управлении.

**Решение:** `OrthoGrid` — сетка, выровненная по потоку:
- Time axis: интегрируем look_point вперёд/назад n_tau шагов
- Ortho axis: шаг ⊥ фазовой скорости от центральной траектории, затем интеграция каждого клона

**Реализация:**
```python
grid_p = OrthoGrid(shared_context, u_sign=+1, name='ort_p')
grid_m = OrthoGrid(shared_context, u_sign=-1, name='ort_m')
```

Два экземпляра для ±u — переключение через _cycle_u().

**Почему именно так:**
- ✅ Визуализирует деформацию фазового пространства (сжатие/растяжение ⊥ потоку)
- ✅ Три режима шага (TIME/ARC/ORTHO) показывают разные аспекты динамики
- ✅ Front lines наглядно показывают, как фронт деформируется при интеграции

**Статус:** ✅ Активно используется

## Decision #22: Три режима шага клонов (TIME/ARC/ORTHO)

**Дата:** 2026-06-20 (сессия 20)

**Проблема:**
Клоны (траектории ⊥ центральной) можно шагать по-разному. Каждый способ показывает свою сторону динамики.

**Решение:** Три режима, переключаемые клавишей 7:
1. **TIME** — все клоны шагают одинаковый dtau (iso-time fronts)
2. **ARC** — клоны match arc length центральной траектории (iso-arc fronts)
3. **ORTHO** — клоны оптимизируют ⊥ фронта к вектору поля через `scipy.optimize.minimize_scalar`

**Почему именно так:**
- TIME = простейший; ARC = учитывает скорость потока; ORTHO = идеальные ортогональные фронты
- Сравнение режимов даёт понимание геометрии потока

**Статус:** ✅ Активно используется

**Проблема:**

- ✅ Оба нужны для OrthoGrid; разделение естественно

**Статус:** ✅ Активно используется

## Decision #24: r_s фиксирует разброс, ds = r_s / n_s

**Дата:** 2026-06-20 (сессия 20)

**Проблема:**
Как параметризовать ⊥-шаг клонов? Если ds фиксирован, то увеличение n_s расширяет область. Если r_s фиксирован, увеличение n_s уплотняет сетку при том же масштабе.

**Решение:** `r_s` фиксирует полный разброс (от центра до крайнего клона), `ds = r_s / n_s`. Увеличение n_s → уплотнение, не расширение.

**Почему именно так:**
- ✅ Пользователь контролирует масштаб визуализации через r_s
- ✅ n_s — «плотность» сетки, не её размер

**Статус:** ✅ Активно используется
